## topic: Why workflows fail, and hearing about it | why-fail
Workflows fail for ordinary reasons: an API is down, a login expired (remember the 7-day Testing mode in p2-3), the data is bad. The question is not *if* it fails but **whether you find out** before the client does.

Two tools:
- an **error workflow** that alerts you when another workflow fails
- node settings that **retry** or **continue** past errors

Also: the **Stop And Error** node deliberately fails a run on a condition you choose (for example "total is negative"), which then triggers the error workflow.

## topic: The Error Trigger and error workflow | error-workflow
An **error workflow** is a separate workflow whose first node is an **Error Trigger**. It runs when another workflow fails.

How to connect them: in the **failing** workflow open **Options, Settings** and pick the error workflow in the **Error workflow** dropdown, then save.

The Error Trigger gives you data about the failure:
- `workflow.name`, `workflow.id`
- `execution.id` and `execution.url` (a link to the failed run; absent if the *trigger itself* failed)
- `execution.error.message` (and the stack trace)
- `execution.lastNodeExecuted`: the node that failed
- `execution.mode`

A useful alert email says: the **workflow name**, the **failed node**, the **error message** and a **link** to the execution. For a client's workflow you'd want that so you can act in minutes.

> Warning: the Error Trigger runs **only for automatic (production) executions**. The docs say you can't test error workflows by running a workflow manually: clicking Execute workflow with a broken node will **not** fire it. You must publish the failing workflow and let its trigger run it.

What if the error workflow itself fails? Then nobody is alerted: keep it very simple (one Error Trigger and one email) and test it.

## topic: Retry On Fail and On Error | retry-on-error
Each node has a **Settings** tab with error options.

- **Retry On Fail**: try the node again if it fails, with **Max Tries** and **Wait Between Tries**. Good for flaky APIs (a request that sometimes times out).
- **On Error**: what the workflow does when the node fails: **Stop Workflow** (default), **Continue** (carry on with the other items), or **Continue (using error output)** (send the failed items down a separate path).

**Think before you retry.** Retrying is only safe if repeating the action is harmless. Reading data from a weather API: safe. **Sending an email**: if the first attempt actually went out but the answer got lost, a retry sends a **duplicate**. Same for creating a payment or a record. That is why you'd retry the HTTP node but not the Gmail node.

> Warning: if **On Error** is set to one of the **Continue** options, n8n ignores Max Tries and Wait Between Tries (reported in n8n's issue tracker). To test retries, leave On Error on Stop Workflow.

> Tip: setting names can differ slightly between n8n versions. Look in the node's Settings tab.

## topic: Doing it | doing-it
1. New workflow `00 error alert`: **Error Trigger**, then **Gmail** sending you the workflow name, the failed node and the error message.
2. In `05 weekly weather digest` open Settings and choose `00 error alert` as the Error workflow.
3. Break the HTTP node on purpose (wrong URL). A manual run will **not** fire the error workflow, so: change the Schedule Trigger to run **every minute** (Minutes rule), **publish** the workflow, and wait for the next run. Confirm you get the email, then unpublish, set the schedule back to daily at 08:00 and fix the URL.
4. Turn on **Retry On Fail** (3 tries) on the HTTP node, and explain why not on the Gmail node.

Done when a deliberate failure emails you, and you can explain when retry is safe and when it isn't.
