## topic: Request and response | request-response
Every API call is one **request** and one **response**. Think of ordering at a counter: you ask, the server answers.

A **request** has:
- a **method**: what you want to do (`GET`, `POST`, ...)
- a **URL**: where to send it
- **headers**: extra information such as who you are (your API key) and what format the body is in
- sometimes a **body**: data you send along

A **response** has:
- a **status code**: a number saying how it went
- **headers**: information about the answer
- a **body**: the data, usually **JSON**

```
Request:   GET https://api.example.com/orders?status=open
           Authorization: Bearer abc123
Response:  200 OK
           Content-Type: application/json
           {"orders": [ ... ]}
```

The parts of a URL: `https://api.example.com/orders?status=open` is the protocol (`https`), the host (`api.example.com`), the path (`/orders`) and the query string (`?status=open`, key=value pairs after the `?`, joined with `&`).
know: Name the parts of a request and a response
know: Name the parts of a URL
Q: Name the four parts of a request and the three parts of a response.
A: Request: method, URL, headers, body (sometimes). Response: status code, headers, body.
Q: In `https://api.example.com/orders?status=open`, what is the path and what is the query string?
A: Path: `/orders`. Query string: `?status=open`.

## topic: Methods and GET vs POST | methods
The **method** says what you want to do.

| Method | Meaning |
|---|---|
| `GET` | read data |
| `POST` | send data to create something or trigger an action |
| `PUT` / `PATCH` | update something (replace / change part) |
| `DELETE` | remove something |

**GET vs POST** (a common mix-up):
- GET puts its parameters **in the URL** (`?city=Amsterdam`). The URL ends up in browser history and server logs, and URLs have a length limit.
- POST puts its data **in the body**.
- **Neither is encrypted by itself.** **HTTPS** (the `s`) encrypts the whole request in transit, for both. So POST does not "hide" data; it only keeps it out of the URL.
- The real difference is **meaning**: GET should only read, and POST changes something. Browsers and tools rely on that.

> Warning: never put an API key or password in a URL query string. It gets logged and saved in history. Use a header.
know: Name the five methods and what each means
know: Explain GET vs POST, including what HTTPS does and does not hide
Q: What is the difference between GET and POST? Does POST hide the data?
A: GET puts parameters in the URL and should only read; POST puts data in the body and changes something. POST doesn't hide data by itself: HTTPS encrypts both.
Q: Why should an API key not go in the URL?
A: URLs are saved in history and server logs, so the key would leak. Put it in a header.

## topic: Status codes | status-codes
The **status code** is a three-digit number in the response. The first digit is the class:

| Code | Meaning |
|---|---|
| `200` OK | it worked |
| `201` Created | it worked and something new was created |
| `3xx` | redirect: the thing is somewhere else |
| `400` Bad Request | your request is malformed |
| `401` Unauthorized | not authenticated (missing or wrong key) |
| `403` Forbidden | authenticated, but not allowed |
| `404` Not Found | no such URL or item |
| `429` Too Many Requests | you hit a rate limit: slow down |
| `5xx` | the server broke (not your fault) |

Rule of thumb: **2xx** success, **4xx** you made a mistake, **5xx** they did. A script must check the status before trusting the body, because an error response can still contain JSON.

know: Explain 200, 201, 400, 401, 403, 404 and 429
Q: What is the difference between 401 and 403?
A: 401: not authenticated (missing or wrong credentials). 403: authenticated but not allowed to do this.
Q: A call returns 429. What happened and what do you do?
A: A rate limit: too many requests. Wait, then retry more slowly.
Q: Who is at fault for a 4xx? For a 5xx?
A: 4xx: the request (me). 5xx: the server.

## topic: Headers and API keys | headers
**Headers** are name: value lines that carry extra information.

- `Content-Type: application/json` says the body is JSON.
- `Authorization: Bearer <key>` carries your API key (some APIs use `x-api-key: <key>` instead).
- `Accept: application/json` says what format you want back.

An **API key** proves who you are, so the service can allow, bill or limit you. It goes in a header, not the URL, and never in code you share. (You stored one safely in `.env` in p0-5.)

If you send a wrong or missing key you get `401`.

know: Say where an API key goes in a request
Q: Which header says the body is JSON, and which carries a key?
A: `Content-Type: application/json` says the body is JSON. `Authorization: Bearer <key>` (or `x-api-key`) carries the key.
Q: You send a wrong API key. Which status code do you expect?
A: 401.

## topic: JSON | json
**JSON** is the text format almost every API uses. It has:
- **objects**: `{ "name": "Anna", "age": 31 }` (key and value pairs, keys in double quotes)
- **arrays**: `[ 1, 2, 3 ]` (ordered lists)
- **strings** in double quotes, **numbers**, `true` / `false`, and `null`

They nest:

```json
{
  "orders": [
    { "id": 1, "paid": true,  "items": ["pen", "ink"] },
    { "id": 2, "paid": false, "items": [] }
  ]
}
```

To reach the second order's id you go step by step: `orders` → second item → `id`. In Python that's `data["orders"][1]["id"]`.

> Tip: JSON needs double quotes, and no trailing commas. A missing comma or a single quote is the usual reason a JSON file "doesn't parse".
know: Read nested JSON and name the data types
Q: In the example, which path reaches `"ink"`?
A: `orders` → first item → `items` → second item. In Python: `data["orders"][0]["items"][1]`.
Q: Name three common JSON mistakes.
A: Single quotes instead of double, a trailing comma, and a missing comma between items.

## topic: Webhooks | webhooks
With a normal API call **you** ask the service for news. A **webhook** is the reverse: you give the service a URL, and when something happens (a payment, a form submission) **the service sends an HTTP POST to your URL**.

```
normal API:  me --GET--> service      (I ask, it answers)
webhook:     service --POST--> me     (it tells me when something happens)
```

That is why automation tools like n8n can give a workflow its own URL for the other service to call. You'll build that in p1-5.
know: Explain a webhook versus an API call
Q: What is a webhook, and how does it differ from a normal API call?
A: A webhook is a URL I give to a service so it sends me a POST when something happens. In a normal API call I ask the service; in a webhook it contacts me.

## topic: Trying it: httpbin and curl.exe | trying-it
httpbin.org is a free service for testing requests. Do these three calls and notice what each shows.

1. Open `https://httpbin.org/get` in your browser. You see JSON describing your request, including the headers your browser sent.
2. Open `https://httpbin.org/status/404` and `https://httpbin.org/status/200`. The page may look empty: the status code is not shown on the page, it is part of the response.
3. In PowerShell run:

```
curl.exe -i https://httpbin.org/get
```

`curl.exe` is a command-line tool that sends a request. `-i` includes the response headers in the output. You see the **status line** first (`HTTP/1.1 200 OK` or `HTTP/2 200`), then the **headers**, then a blank line and the **body**.

> Warning: type `curl.exe`, not `curl`. In PowerShell `curl` is an alias for a different command (`Invoke-WebRequest`) that behaves differently.
cmd: `curl.exe -i URL` | sends a GET and prints the status line, headers and body
know: Find the status line, headers and body in curl.exe output
Q: Why do you type `curl.exe` and not `curl` in PowerShell?
A: In PowerShell `curl` is an alias for a different command, Invoke-WebRequest. `curl.exe` is the real curl.
Q: What does `-i` add to curl's output?
A: The response headers (and the status line) before the body.
