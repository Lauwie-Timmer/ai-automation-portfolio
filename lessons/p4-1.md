## topic: Idempotency: don't do the same thing twice | idempotency
A workflow that runs on a timer will look at the same data again and again. **Idempotent** means: running it twice has the same effect as running it once. Without it, a workflow that checks for signups every 15 minutes would find the *same* signup 96 times a day and email you 96 times.

The standard fix is a **marker** that says "already handled":
- a column such as `notified` (true or false) on the row itself, or
- a list of ids you have already processed, kept somewhere (a sheet, a table).

The flow becomes: **find rows where `notified` is false, handle them, then set `notified` to true**. Next run, those rows no longer match, so nothing happens twice.

Order matters. If you set the marker *before* you send the email and the email fails, the signup is never notified. If you set it *after*, a crash between the two steps can cause one duplicate. For a notification to yourself a rare duplicate is the better failure, so mark *after* the action succeeds.

> Tip: also test the "nothing to do" case. When there are zero new rows the workflow must stop quietly instead of sending an empty email.

## topic: Least privilege and Supabase keys | keys
**Least privilege** means giving a tool only the access it needs. A key that can read and write your whole production database is dangerous to leave in a tool: if it leaks, everything leaks.

Supabase has two kinds of API key (checked in Supabase's docs, October 2026):
- **Publishable key** (`sb_publishable_...`): safe to ship in a web page or app. It respects **Row Level Security (RLS)**, the rules that decide which rows a user may see.
- **Secret key** (`sb_secret_...`): for servers only. It **bypasses RLS completely**. Older projects have the same thing under the name **service_role** key; Supabase is phasing the old `anon` and `service_role` keys out by the end of 2026.

n8n runs on a server you control, so n8n's Supabase credential uses the **secret key**. That is allowed, but treat it like a password: keep it **only in the n8n credential**, never in a repo, a screenshot, a prompt or a chat message.

Rules for this project:
1. Build against a **separate practice project** with fake data first.
2. Only then decide whether to connect a real one, and prefer a read-only way in or a dedicated table.
3. Never paste a secret key anywhere except the credential field.

> Warning: if a secret key ever leaks, rotate it in Supabase straight away (create a new one and disable the old one).

## topic: Polling, webhooks and consent | polling
**Polling** means your workflow asks "anything new?" on a timer (the **Schedule Trigger**). A **webhook** means the other side calls you the moment something happens.

Your n8n runs on `localhost`, which only your own computer can reach. Supabase can't call a localhost address, so for this project **polling is the right choice**, and every 15 minutes is plenty. Webhooks from outside tools come back in p4-i and in p6-4, where you learn about a public URL.

**Consent:** only email the people who signed up if the signup form told them they would hear from you. When in doubt, notify only yourself, as this project does. People on a waitlist did not agree to marketing by joining it.

1. **Schedule Trigger**, Mondays at 08:00.

## topic: What can go wrong | failures
These are the questions your Checker will ask. Have an answer ready.

- **Supabase is down or the key is wrong:** the Supabase node fails, the error workflow emails you, and nothing is marked, so the next run retries. Nothing is lost.
- **Two runs overlap** (the first is slow, the second starts): both can read the same unmarked row and notify twice. For a notification to yourself that is acceptable. To prevent it, mark the row first or use a single status column such as `pending`, `sent`.
- **A row is edited:** if you only look at `notified`, edits are ignored. That is correct for "tell me once", but you must decide on purpose.
- **The key leaks:** rotate the secret key in Supabase, update the n8n credential, and check the project's logs.

The honest answer to "what if X" is rarely "it can't happen". It is "this is what happens, and this is why that is acceptable (or what I would change)".
