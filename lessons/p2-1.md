## topic: Trigger, node and workflow | trigger-node
You already used these in Phase 1. Here they get exact definitions, because every tutorial and every client conversation uses them.

- **Workflow**: the whole automation, a chain of nodes on a canvas.
- **Trigger**: the node that starts a workflow. Every workflow has at least one. Common triggers: **Webhook** (an HTTP call arrives), **Schedule** (a clock time), **Manual** (you click Execute workflow), and app events (a new email, a new row).
- **Node**: one step. A node does a single job: call an API, change data, make a decision, send an email.

A client says: "When someone fills in my form, add them to a sheet and email me." In n8n words: the **trigger** is the form (a webhook), then one node writes to the sheet and another sends the email.

Q: What is a trigger? Name three kinds.
A: The node that starts a workflow. Webhook, Schedule and Manual (also app events).
Q: A client says "every Monday send me a report". Which trigger do you use?
A: A Schedule trigger.

## topic: Items | items-recap
**Item**: one JSON object flowing through the workflow. A node usually runs **once per item**: 10 items in means 10 runs of the node's job. This is the most important idea in n8n, and the source of most beginner bugs.

Scenario: a webhook receives a list of 10 orders as 10 items. The next node, say "send email", runs **10 times** and sends 10 emails. If you wanted one summary email you must first combine the 10 items into one. (You learn the nodes for that in p2-4.)

Inside a node you can look at items in the Schema, Table and JSON views of the Input and Output panels. When a result is surprising, count the items first.
know: Explain that a node runs once per item
Q: A webhook delivers 10 items and the next node sends an email. How many emails go out and why?
A: 10, because the node runs once per item.
Q: Where do you check how many items a node received?
A: In its Input and Output panel (the item count is shown, and the Table/JSON view lists them).

## topic: Expressions | expressions-recap
An **expression** is `{{ ... }}` code that reads data. Examples:

```
{{ $json.email }}                         a field of the current item
{{ $('Webhook').item.json.name }}         a field from an earlier node, by its name
```

`$json` is the **current item's** data. `$('Node name')` reaches a specific earlier node. Which one you need depends on where the data is: if it arrived straight from the previous node, `$json` works; if a node in between changed the data, use `$('Node name')` to reach the original.

Use an expression for light work (read a field, a short calculation). When the logic gets complex, use a data node such as Edit Fields instead (later you'll meet a node that runs your own code): an expression shows an immediate preview, while a big one is hard to read.

Q: When do you need `$('Webhook')` instead of `$json`?
A: When the data I need came from an earlier node, not from the node right before this one.
Q: When should you switch from an expression to a data node?
A: When the logic is complex, such as restructuring arrays or aggregating, instead of just reading or lightly calculating a value.

## topic: Credentials | credentials
**Credentials** are stored logins and keys. You enter them **once** in n8n, where they are saved encrypted. Nodes then pick them from a dropdown.

Why this matters:
- Credentials are **not part of the workflow file**. When you export a workflow (p2-7) it contains the credential's *name*, not the secret. You can share a workflow safely.
- You don't paste keys into nodes, so keys can't leak in screenshots or exports.
- Name them clearly (for example `Google (dev)` and `Google (prod)`) so you never mix a test with real data.

Never paste a credential's secret into chat or your repo, the same rule as for your `.env` in p0-5.
know: Say what credentials are and that they are not in the workflow file
Q: Why can you share an exported workflow without leaking your passwords?
A: Credentials are stored separately and encrypted. The export only contains their names.

## topic: Execution, active and pinned data | execution-active-pinned
- **Execution**: one run of a workflow. The workflow's **Executions** tab lists past runs with their data. This is how you debug: open a run and see what each node received.
- **Published vs unpublished** (older n8n versions said **Active**): only a published workflow reacts to its production trigger (a schedule or the production webhook URL). **Manual test runs** work either way. In current n8n, **Save** only saves your draft; the production trigger keeps running the **last published version**. After you change a published workflow, click **Publish** again, or production keeps using the old version.
- **Pinned data**: in a node's Output you can click **Pin data**. The node then reuses that output instead of calling the API again, so you can build the next step on stable data. It only applies while testing: production runs ignore pinned data. Click **Unpin** to fetch fresh data. Nodes with binary data can't be pinned.

To debug a failed production run: Executions tab, pick the run, **Debug in editor** (for a successful one: **Copy to editor**). n8n copies the run's data into the editor and pins it in the first node, so you can reproduce the problem.

Q: A workflow works when you click Execute workflow but nothing happens from the production webhook. What is the likely cause?
A: The workflow isn't published (active). Only published workflows react to their production trigger.
Q: You edited a published workflow and clicked Save, but production still behaves the old way. Why?
A: Save only stores a draft. Production runs the last published version until I click Publish again.
Q: What does pinning data do and when does it not apply?
A: It reuses a node's output instead of calling the API again while testing. It is ignored in production runs.
Q: How do you reproduce a failed production run in the editor?
A: In the Executions tab choose the run and click Debug in editor.
