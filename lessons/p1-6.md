## topic: The three places in Git | three-places
Git tracks your files in three places:

```
working folder  --git add-->  staging area  --git commit-->  history
(files you edit)              (the next commit)               (saved versions)
```

- **Working folder**: the files as you see and edit them.
- **Staging area**: a waiting room. `git add` puts changes there, so you choose what goes into the next save point.
- **History**: the commits. A **commit** is a saved version with a message, a time and an author. You can return to any of them.

`git status` tells you which files are changed, which are staged and which are not tracked. Run it before and after everything: it is how you know where you are.

A commit message says **what changed and why**, in a short line: `Add Phase 1 scripts and workflows`.
cmd: `git status` | shows changed, staged and untracked files
cmd: `git add .` | stages all changes in the current folder for the next commit
cmd: `git commit -m "message"` | saves the staged changes as a commit

Q: What is the difference between `git add` and `git commit`?
A: `git add` puts changes into the staging area. `git commit` saves what is staged as a version in the history.
Q: Why is there a staging area at all?
A: So I can choose exactly which changes go into the next commit.
Q: What does `git status` show, and when do you run it?
A: Which files are changed, staged or untracked. Before and after every step, so I know where I am.
Q: What belongs in a good commit message?
A: A short line saying what changed and why, e.g. "Add Phase 1 scripts and workflows".

## topic: First-time setup and pushing | setup-push
Git needs to know who makes the commits. Do this **once** per computer:

```
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

`--global` means for every repo on this PC. Use the email of your GitHub account (or the private no-reply address GitHub offers).

Commits are local until you **push** them:

```
git push
```

`git push` uploads your new commits to GitHub (the remote). The opposite is `git pull`, which downloads commits from GitHub that you don't have yet. On your first push a browser window may ask you to sign in to GitHub: that's normal.

After pushing, open your repo on github.com and look: your files are there.
cmd: `git config --global user.name "Your Name"` | sets your name for all commits, once
cmd: `git config --global user.email "you@example.com"` | sets your email for all commits, once
cmd: `git push` | uploads your commits to GitHub
cmd: `git pull` | downloads new commits from GitHub
know: Set your name and email once
know: Push commits and see them on GitHub
Q: What does `git push` do, and what does `git pull` do?
A: `git push` uploads my commits to GitHub. `git pull` downloads commits I don't have yet.
Q: Why do commits not show on GitHub right after `git commit`?
A: A commit is local. It only reaches GitHub after `git push`.
Q: Which two commands set your identity, and how often do you run them?
A: `git config --global user.name "..."` and `git config --global user.email "..."`, once per computer.
Q: What does `--global` mean in those commands?
A: The setting applies to every repo on this PC.

## topic: Branches and merging | branches
A **branch** is a separate line of work. It lets you experiment without risking the working code on `main` (the main branch).

```
git switch -c experiment     make a branch called experiment and move onto it
git status                   shows "On branch experiment"
(edit a script)
git add .
git commit -m "Try a change"
git switch main              go back to main (your edit is not here)
git merge experiment         bring the branch's commits into main
git log --oneline            one line per commit, newest first
```

`-c` means "create". `git switch name` moves between branches. **Merging** combines the branch's commits into the branch you are on, so be on `main` first. If both branches changed the same lines, Git reports a **conflict** and you must choose the right version by hand before committing. Nothing is lost.
cmd: `git switch -c experiment` | creates a branch and moves onto it
cmd: `git switch main` | moves back to the main branch
cmd: `git merge experiment` | brings the experiment branch's commits into the branch you are on
cmd: `git log --oneline` | lists commits, one line each, newest first
know: Create a branch, commit on it, switch back and merge
know: Say what a branch and a merge are for
Q: What is a branch for?
A: A separate line of work, so I can experiment without risking the working code on main.
Q: Before `git merge experiment`, which branch must you be on?
A: `main`: a merge brings the other branch into the one I'm on.
Q: What is a merge conflict?
A: Both branches changed the same lines, so Git can't choose. I pick the right version by hand, then commit.

## topic: Secrets and mistakes | secrets-undo
**Never commit `.env`** (a key or password). It is in `.gitignore` for that reason (p0-5). If you commit a secret by mistake:
1. **Delete the key** in the provider's console and create a new one. This is the fix that matters.
2. Deleting the file in a later commit does **not** remove it from the history, and anyone who cloned or saw the repo may already have it.

To undo a commit that is **not pushed yet**, keeping your changes:

```
git reset --soft HEAD~1
```

`HEAD~1` means "one commit before the latest". `--soft` moves the branch back but keeps your changes staged, so you can fix them and commit again. Don't rewrite history that you already pushed to others.

> Tip: `git status` before every commit. If you see `.env` or `.venv` in the list, stop and fix `.gitignore` first.
cmd: `git reset --soft HEAD~1` | undoes the last local commit but keeps the changes staged
know: Say what to do after committing a secret
know: Undo the last unpushed commit
Q: You committed a file with your API key. What do you do first?
A: Delete that key in the provider's console and create a new one. Removing the file later doesn't remove it from history.
Q: How do you undo the last commit if you haven't pushed it, keeping your work?
A: `git reset --soft HEAD~1`
