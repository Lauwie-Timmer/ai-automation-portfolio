## topic: Why a virtual environment | why-venv
Python programs use **packages**: pieces of code other people wrote, such as `requests`. Without any setup, every project on your PC shares one pile of installed packages. Project A needs version 1 of a package, project B needs version 2, and eventually they break each other.

A **virtual environment** is a private folder, called `.venv`, that holds the exact Python packages **one project** uses. Each project gets its own, so they can't interfere. You can delete `.venv` and rebuild it without harming anything else.

```
C:\dev\automation-portfolio\
    .venv\            <- this project's own packages (not uploaded to GitHub)
    README.md
```

`.venv` is listed in `.gitignore` (the Python template does this). It is big, it can be rebuilt, and it is specific to your PC, so it doesn't belong on GitHub.

## topic: pip, requests and PyPI | pip-requests
**pip** is the program that installs Python packages. It downloads them from **PyPI**, the public package library on the internet. You run it as `python -m pip install name`, which makes sure it uses the same Python you are running.

**requests** is the standard library for making **HTTP calls** from Python: asking a website or API for data, or sending data to it. You will use it in Phase 1. Installing it now proves your setup works.

```
python -m pip install requests
```

pip prints "Successfully installed requests-..." and the packages it depends on. Where it installs them depends on whether a virtual environment is active (next topic).
cmd: `python -m pip install requests` | installs the requests package into the active Python

## topic: Creating and activating | create-activate
**Create** the environment once, in the project folder:

```
cd C:\dev\automation-portfolio
python -m venv .venv
```

`python -m venv .venv` means: run Python's `venv` tool and make a folder named `.venv`. It takes a few seconds and prints nothing when it works.

**Activate** it every time you open a new terminal for the project:

```
.\.venv\Scripts\Activate.ps1
```

Activating tells the terminal to use **that folder's** Python and pip. Your prompt then starts with `(.venv)`:

```
(.venv) PS C:\dev\automation-portfolio>
```

If you **forget to activate**, `pip install` goes into your global Python, the shared pile you wanted to avoid, and your project won't find the package. If you see no `(.venv)`, you're not active.

If Windows blocks the script ("running scripts is disabled"), run this once and try again:

```
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

That lets your own user run local scripts. It's a security setting, so do it only for the reason above.

To leave the environment, type `deactivate`.

cmd: `.\.venv\Scripts\Activate.ps1` | activates it, so the prompt starts with (.venv)
cmd: `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` | allows your user to run local PowerShell scripts, once

## topic: Testing and requirements.txt | test-requirements
**Test** that the package works by importing it from Python:

```
python -c "import requests; print(requests.__version__)"
```

`python -c "..."` runs the code in quotes. If it prints a version number, requests is installed. A `ModuleNotFoundError` means it isn't, usually because the environment wasn't active when you installed.

**requirements.txt** is a text file listing the packages and versions the project uses, so anyone (or you, on another PC) can rebuild the environment with one command. You create it from what's installed:

```
pip freeze > requirements.txt
```

`pip freeze` prints the installed packages. `>` sends that output into a file instead of the screen. To rebuild on a fresh PC: create and activate a venv, then `python -m pip install -r requirements.txt`.

> Tip: in older Windows PowerShell (version 5.1) `>` may save the file as UTF-16, which GitHub shows as unreadable text. If `requirements.txt` looks garbled on GitHub, recreate it with `pip freeze | Out-File -Encoding utf8 requirements.txt`.

Last, in VS Code press **Ctrl+Shift+P**, choose **Python: Select Interpreter**, and pick the one inside `.venv`, so VS Code uses the same Python as your terminal.

## topic: Checking your work | checking
When the step is done, all of these are true:

1. `(.venv)` shows in your prompt in `C:\dev\automation-portfolio`.
2. `python -c "import requests; print(requests.__version__)"` prints a version.
3. `requirements.txt` exists in the folder (check with `ls`).
4. `.gitignore` contains `.venv` (the Python template does). Check by opening the file in VS Code, or run `git status`: `.venv` must **not** appear in the list.
5. VS Code's selected interpreter is the one in `.venv`.

> Tip: if `.venv` shows up in `git status`, the line `.venv` is missing from `.gitignore`. Add it on its own line.
cmd: `git status` | should not list .venv, because it is ignored
