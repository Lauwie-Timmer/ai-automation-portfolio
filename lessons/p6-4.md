## topic: Docker Compose and Kubernetes | compose
**Docker Compose** describes one or more containers in a single file (`compose.yaml`), so a server can be rebuilt with one command. It is the realistic next step after the plain `docker run` you already know. A typical small setup is **n8n plus a database and a reverse proxy for HTTPS.**

```
docker compose up -d        start everything in the file, in the background
docker compose ps           show what is running
docker compose logs         show the output
docker compose down         stop and remove the containers (data in volumes stays)
```

**Kubernetes** runs and manages many containers across many servers: it restarts failed ones, adds copies under load and updates without downtime. Large companies use it widely. For a small client's handful of workflows it adds a lot of **complexity and cost for no benefit**, so you don't need it. Know the word; learn it only if a real project requires it.
cmd: `docker compose up -d` | starts every container in compose.yaml in the background
cmd: `docker compose ps` | lists the containers of the compose project
cmd: `docker compose down` | stops and removes the containers (volumes stay)

## topic: Watching it and keeping it safe | watch
Three monitoring checks to set up for a client:
1. **Spending limit and alerts** in the AI provider's console (where the keys live), so a runaway workflow can't cost a fortune.
2. **Execution clean-up:** n8n deletes old execution data automatically. By default `EXECUTIONS_DATA_PRUNE` is **true**, `EXECUTIONS_DATA_MAX_AGE` is **336 hours** (14 days) and `EXECUTIONS_DATA_PRUNE_MAX_COUNT` is **10,000**. Check the defaults for your version in the n8n docs and set them to what the client needs.
3. **Uptime check:** a free service such as UptimeRobot calls n8n's **`/healthz`** address and emails you if it stops answering. `/healthz` returns 200 when the instance is reachable; `/healthz/readiness` also checks that the database is connected. UptimeRobot's free plan checks every 5 minutes (checked October 2026; read its terms for commercial use).

**A server needs:** regular **updates**, a **backup**, **HTTPS**, strong passwords and someone **watching for failures.**

## topic: Backups and the encryption key | backup
n8n **encrypts saved logins** (credentials) with an **encryption key**. For a self-hosted n8n it lives in the `.n8n` folder's `config` file, or you set it yourself in the `N8N_ENCRYPTION_KEY` environment variable. If you lose the data and the key, **every saved login becomes unreadable**, and the docs say it can't be recovered unless you made a decrypted export beforehand.

**Back up:**
- the **`.n8n` data volume** (it holds the key and, if you use SQLite, the database);
- the **external database** if you use PostgreSQL;
- any external binary or execution storage.

**CLI exports** (p2-8) contain workflows and credentials only. They **do not** include users, execution history, variables or the **encryption key**, so they are not a full backup.

Offer a **handover**: workflow exports, a README and a recording of how it works. **Monthly maintenance is a paid extra, so quote it separately.**
