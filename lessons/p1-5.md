## topic: The Webhook node and its two URLs | two-urls
A **Webhook node** is a trigger that gives your workflow a URL. Anything that sends an HTTP request to that URL starts the workflow. It accepts GET, POST, PUT, PATCH, DELETE and HEAD; for your Python script you'll use **POST**.

n8n shows **two** URLs for the same webhook:

| | Test URL | Production URL |
|---|---|---|
| Path | `/webhook-test/<path>` | `/webhook/<path>` |
| Works when | you click **Listen for test event** (or Execute workflow), only once | the workflow is **published** (older versions: **Active**) |
| Where you see the data | right in the node's Output | **not** in the editor: in the workflow's **Executions** tab |
| Use it for | building and testing | real use |

Why two? While building you want to *see* the data arrive in the editor (test). Once finished you want it to run by itself, always (production).

> Tip: if the test URL gives "not registered" or 404, you forgot to click **Listen for test event** first, or it already received one call. If the production URL gives 404, the workflow isn't published yet. If you changed a published workflow, publish it again: Save alone doesn't update what the production URL runs.

A: Test URL: works while I'm listening for a test event, shows data in the editor. Production URL: works once the workflow is published, runs without the editor and appears in Executions.

## topic: Reaching n8n from Python | reach-n8n
Your Python script runs on your PC. n8n runs in a container. They meet through the **port mapping** `-p 5678:5678` from p0-3: your PC's port 5678 leads into the container. So the script posts to `http://localhost:5678/webhook-test/portfolio-test` and it arrives inside n8n.

**But** a webhook on `localhost` can be reached **only from your own PC**. Services on the internet (Stripe, GitHub, a form site) can't call it, because `localhost` means "this computer" for every computer. To receive calls from the internet you need a **public URL**: a hosted n8n, or a tunnel. We cover that when a job needs it.

By default the webhook replies immediately with a short message ("Workflow got started"). In Phase 2 you'll learn to control that answer, for example to return data to the caller.

Q: How does a Python script on your PC reach n8n inside Docker?
A: Through the port mapping -p 5678:5678: localhost:5678 on my PC leads to port 5678 in the container.

## topic: What arrives in the webhook | webhook-data
The Webhook node's output is **not** just your JSON. It wraps the request in several parts:

```json
{
  "headers": { "content-type": "application/json", "x-source": "python" },
  "params": {},
  "query": {},
  "body": { "name": "test", "message": "hello from python" }
}
```

Your payload sits under **`body`**. So the expression to read your `message` field is:

```
{{ $json.body.message }}
```

not `{{ $json.message }}`. If an expression comes back empty, open the Output **JSON** view and check where the field really is.

Add an **Edit Fields** node after the webhook that keeps only `message` and adds a field `received_at` with the expression `{{ $now }}`. (Turn on Keep Only Set Fields, as in p1-4.)

Q: Your script posts `{"message": "hi"}`. What expression reads it in the node after the webhook?
A: `{{ $json.body.message }}`
Q: Where are the request headers in the webhook output?
A: Under the `headers` key, next to `body`, `params` and `query`.

## topic: Doing it step by step | doing-it
1. New workflow `02 receive webhook`. Add a **Webhook** node: method **POST**, path `portfolio-test`.
2. Click **Listen for test event**. Copy the **Test URL**, put it into `post_webhook.py` (from p1-3) and run it. Watch the data arrive in the node's Output.
3. Add the **Edit Fields** node described above.
4. **Save** the workflow, then **publish** it (the button at the top right; in older versions you switch it to **Active**). Point the script at the **Production URL** and run again.
5. Open the workflow's **Executions** tab and click the run. Production runs are visible there, not in the editor.
